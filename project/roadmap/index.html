    Goals and decisions¶

    • Autonomous dynamical-system forecasting is the easiest default workflow.
    • Presets and custom DAGs use the same fit, forecast, tune and save lifecycle.
    • Keep the expressive functional construction API, similar to building a Keras functional model. pytorch_symbolic remains supported while its limitations and available standard PyTorch alternatives are evaluated. Changing the backend must preserve that construction experience.
    • Prefer existing PyTorch, Optuna, Graphviz, SciPy and TSDynamics capabilities. Add a ResDAG abstraction only when a demonstrated requirement needs it.
    • Keep every component replaceable through public interfaces: initializers, cells, state, transforms, readouts, solvers, objectives and search spaces.
    • Automatic defaults must be dependable; users can force the solver, precision, device, preprocessing and execution choices.
    • Learn preprocessing from training data and return forecasts in original units. Keep preprocessing configurable and optional.
    • The common PyTorch workflow applies fitted preprocessing in model(x) and returns original units; model.graph(x) exposes the raw graph. Calls carry reservoir state by default. One output returns a tensor; several outputs return a dictionary keyed by their declared names.
    • Provide explicit delayed feedback connections and named inputs/outputs.
    • Keep TSDynamics optional, with first-class trajectory input/output.
    • Tuning has quick, balanced and thorough presets. Balanced is the default; the winning model is fitted and ready to forecast afterward.
    • Compare forecast accuracy, speed and memory together. Publish reproducible workload-specific results and distinguish measured hardware from skipped checks.
    • Breaking simplifications belong in a major release with migration guidance. Consult the maintainer before major implementation choices.

    Phase 2: one functional workflow¶

    The phase-two design note distinguishes agreed behavior, the agreed construction API, and implementation progress. The maintainer has approved rd.Model(inputs={...}, outputs={...}); later major choices still require consultation before implementation.

    Current boundary: phase 1 orders algebraic fitting inside standard nn.Sequential, but the explicit-state and compiled backends cannot thread state through reservoirs hidden inside containers.     Trajectory increment¶

    The trajectory guide covers direct fit(trajectory), default trajectory forecasts, the explicit tensor option, configurable resampling and portable checkpoints. Uniform time axes are the normal case; irregular axes are resampled automatically with linear, PCHIP or cubic interpolation. Explicit sampling intervals preserve the last observed time and never extrapolate. Future histories use the fitted interval.

    The integration adds independent physical-time oracles, source/clock/schema validation, real TSDynamics simulation, failed-refit isolation, legacy checkpoint and optional-dependency tests. Its runnable guide is included in the installed-dynamics CI lanes on Python 3.12–3.14, so missing optional packages cannot silently skip integration verification. This was an intermediate delivery; the completion record below covers the remaining phase-two work.

    SQ-01: one-pass training of cascaded-readout DAGs¶

    Baseline problem. The previous trainer used fitting hooks inside repeated whole-graph warmup/training passes. This produced correct downstream states, but repeated upstream work whenever a fitted readout feeds another reservoir. For a chain of K comparable reservoir/readout stages, propagation can cost O(K² × T), where T is the sequence length. Phase-one correctness remains covered by P1-03; this phase-four task removes the unnecessary computation while preserving it.

    Required execution. Initialize training states once using the current fit reset contract. Traverse the graph in topological order, pausing at each readout to fit it before continuing into its downstream dependencies:

    1. Run reservoir₁ through its warmup prefix, then its training samples, carrying state continuously between the two portions. Retain the resulting features.
    2. Fit readout₁ using only the training features and their aligned targets. Apply the fitted readout to both the warmup and training features.
    3. Continue from those outputs into reservoir₂. Its warmup now uses the fitted upstream mapping; continue through its training portion without resetting between warmup and training. Fit readout₂ and proceed in the same way.
    4. For branches, reuse computed outputs across consumers. Execute a merge only when all its inputs are available, and release retained tensors after their last consumer. Each reservoir node processes its sequence once.

    This is one batch-training traversal of the DAG: a readout waits until its incoming training features are available, solves once, then forwards the full prefix using its fitted weights. It must not restart at the graph input, run downstream reservoirs prematurely, or substitute target values for the fitted upstream readout's actual outputs. Reuse the existing execution plan, fitting interfaces and PyTorch tensor operations; no replacement graph framework is needed. Preserve target alignment, washout, preprocessing, final state and failed-fit isolation across supported graph structures.

    Acceptance checks.

    • Compare fitted weights, downstream features, final states and forecasts with an independent manual layer-by-layer reference. Include nonzero warmup, deliberately wrong initial upstream weights, multiple recurrent fitting boundaries, branches, shared ancestors, merges and supported containers.
    • Instrument reservoir calls and processed samples. Each reservoir graph node must consume exactly its warmup plus training samples once, and each readout must fit once. These structural checks must catch whole-graph replay even if a small wall-clock benchmark happens to pass.
    • Preserve the ordinary single-readout fast path and existing numerical, device/dtype, state-noise and failure-cleanup contracts. Unsupported opaque composites must fail clearly rather than silently assume an execution order.
    • Benchmark depths 1, 2, 4 and 8 at fixed sequence length, widths, dtype, device and thread count. Report propagation and readout-solving time separately, along with peak memory and repeat variability. Propagation work should grow with graph size rather than quadratically with cascade depth; do not hide regression by weakening existing performance thresholds.

    Scheduling. Included in phase four at the maintainer’s request. Implementation and independent verification are complete. Coordinate trainer and execution plan changes with artifact work; consult the maintainer before introducing major public API or memory-policy changes.
