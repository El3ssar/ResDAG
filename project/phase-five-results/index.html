    Phase five measurements¶

    The continuation separates three questions: whether stored models keep their predictions, how well newly initialized models forecast, and what the execution changes cost or save. PR #465's implementation is released in v5.0.0. The roadmap tracks the CPU follow-up and remaining work; each measurement identifies its own source revision.

    Fresh vanilla recipe follow-up¶

    The separate validation and held-out study now completes 48 validation trials and 180 final forecasts. Lorenz retains its ≥10.016 LT trajectory-median result; the selected Rössler recipe improves from 3.013 to 6.750 LT at the main 0.3 threshold (7.154 LT at 0.5). Both winners retain the current input in their readout. All final predictions replay byte for byte after cleanup. The main Rössler target remains open, and this recipe study does not change the comparative CPU findings below.

    Current all-PyTorch closeout¶

    The latest checks cover composition inside a trainable PyTorch network, parallel CPU forecasting, independent-trajectory accuracy and saved-experiment replay. Model execution stays entirely in PyTorch. CPU teacher-forced compilation and the private SciPy recurrence backend are not added.

    An encoder → fitted reservoir → prediction head passes independent tensor and finite-difference gradient checks, repeated optimizer updates, explicit-state chunking and standard state-dictionary reload. Vanilla, OTT and named multi-head graphs also pass full-graph forward/backward capture with PyTorch's AOT eager backend. CPU and native MPS forward/backward checks reject host scalar reads and cross-device tensor operations in the tested hot path. These establish composition correctness; AOT eager capture and MPS checks do not measure CUDA throughput. CUDA is unavailable on this host.

    The acceptance tests found integration defects. CPU autocast could request an unsupported low-precision CSR multiplication; that operation now uses the stored weight precision on the same device, preserving gradients through the surrounding mixed-precision network. Full-graph capture could fail while inspecting the stored state's grad_fn; the compile-aware guard now detaches only carried state under the existing default. Current-call gradients and explicit cross-call gradient retention remain covered. Hosted Torch 2.10 checks on Python 3.11–3.13 also exposed evaluation of a typing union inside the preprocessing getter. Quoting that typing-only argument preserves its eager identity operation and lets Dynamo capture the forward graph; all four compiled cases and the full pipeline selection pass in an isolated Python 3.13/Torch 2.10 reproduction.

    The experiment guide now saves resolved settings, versions, split identities, artifact hashes and exact replay data. Its verification command loads the saved models and reproduces predictions and scores without integrating a system, tuning or fitting again. Recorded timings remain observations from the original run.

    Parallel CPU forecast¶

    The adopted single-frame path removes redundant sequence-wrapper work during closed-loop forecasting in the built-in parallel model. It keeps the original projection and recurrent arithmetic, warmup and state semantics. Hooks, overridden methods, custom activations/readouts, autocast and non-CPU devices use the ordinary compatible path.

    Two fresh-process ABBA blocks compare frozen source snapshots differing only in this parallel implementation. The four synthetic workloads use float64, 150 units per patch, 501 training observations, 100 washout/history observations and a 129-step forecast; patch core width is four and halo width six. Torch and native pools are verified at one thread. Construction is outside the clock; public fit and history-plus-forecast calls are inside it.

    All 64 timed fit/forecast pairs and 32 discarded warmup pairs retain exact fitted tensors, fit states, complete predictions and final forecast states across variants. Each block contains four fresh processes in ABBA order, with one warmup and two timed repetitions per case/process. The ratios below divide the block's pooled baseline median by its candidate median; two blocks are descriptive process observations, not confidence intervals.

    Batch / patches Forecast ratio, block 1 / block 2 Fit control ratio, block 1 / block 2
    1 / 8 1.098 / 1.055 0.981 / 1.004
    1 / 64 1.041 / 1.078 0.973 / 1.015
    4 / 8 1.096 / 1.096 0.956 / 0.982
    4 / 64 1.023 / 1.041 0.929 / 0.996

    Forecast elapsed time falls by about 2–9% in these workloads. Fitting does not use the new path: its unchanged control varies from about 1.5% faster to 7.6% slower. Read these small forecast gains with that control variation in mind. This is bounded parallel-forecast evidence, not a universal training improvement or a cross-library speed ranking. All 96 workflows also preserve their exactness hashes from the earlier run before the typing-only compiler fix. The earlier parallel patch-scaling failure was not reproduced with the current benchmark recipe; its threshold is unchanged.

    Independent trajectories¶

    Six previously selected recipes were frozen before generating ten new trajectories: five initial conditions for each system. Each recipe/system is refitted on each trajectory's own training prefix with three new reservoir seeds, then evaluated at three nonoverlapping forecast origins. There is no new hyperparameter search or winner selection. All 90 fits and 270 forecasts complete with finite predictions; no failed runs are excluded.

    The four primary recipes come from the corrected-initialization capability study. At the main 0.3 normalized-error threshold, the preregistered aggregate is the median of the five trajectory medians; each trajectory median contains nine seed/origin forecasts. The independent unit is a trajectory, not each of the 45 nested forecasts. Full individual ranges include censored lower bounds. Each recipe retains its own selected size and settings; this is not an architecture ablation with matched hyperparameters.

    The two secondary state-only vanilla recipes from the common-family comparison reach the ten-Lyapunov-time median limit on both systems. They use different feature/solver policies and remain separate from the primary friendly recipes. This demonstrates sensitivity to the chosen recipe; it does not replace the negative friendly-vanilla results. The 7–8-time typical-performance target is still unmet for those two frozen friendly recipes. OTT meets the median target in this study, although individual forecasts can be shorter.

    These are robustness checks of frozen recipes refitted on independent runs, not zero-shot transfer of one trained reservoir to a new initial condition. They do not compare competitor accuracy on this new bank or establish that an implementation change caused the vanilla shortfall. Previously inspected forecast banks remain distinct from these new observations.

    A paired regression for the initial implementation separately repeats the same 90 fits and 270 forecasts on clean baseline eb70bf11, using the sealed observations and initial weights. Every fitted-tensor fingerprint, complete prediction, final state and score matches exactly. This second pass adds no tuning or test-based selection.

    The preregistered runtime was frozen before the release-metadata rebase. Its version literal is 5.0.0. Subsequent changes update that literal to 5.0.1, tighten a parallel-only custom-readout guard unused by these six recipes, and quote the preprocessing getter's typing-only cast for older compiler support. The public record retains the original source and every subsequent source bridge; it does not relabel the frozen capture as a later checkout.

    On the final corrected runtime, a separate replay loads all 90 original fitted checkpoints and reproduces all 270 forecasts exactly, including complete prediction bytes, final states and both scores. Every fitted tensor fingerprint also matches; the common graph's nonpersistent post-fit state is restored by the original teacher-forced input prefix. This replay performs no readout solve, fitting, integration or tuning. Two stopped restore-setup attempts are retained separately; neither found a forecast discrepancy or contributes to the original study's scores.

    CPU follow-up¶

    PR #466 is merged as 3b34005 and released in v5.0.1. All four post-merge full suites, three TSDynamics lanes, the published-wheel fit/forecast/save/load replay and live documentation deployment pass.

    The adopted CPU changes reuse AutoReadout residual diagnostics when its admitted Gram solution is unchanged, while recomputing them after a fallback replaces the coefficients. Sparse cycle normalization uses an analytic spectrum, fixing iterative eigensolver failures without dense allocation. The CSR fixes also handle complex value views and explicitly stored zero weights. Automatic storage, solver and compilation choices retain their established settings.

    The experimental timestep-view and driver-slicing rewrites in dc695a6 were rejected: the measurements did not establish a CPU benefit. The original sequence-loop and driver slicing are retained. Records against dc695a6 below remain historical candidate evidence; they do not measure the final adopted implementation's whole-workflow speed.

    Adopted readout reuse and exploratory compilation¶

    A bounded AutoReadout probe fits two well-conditioned Gaussian problems with 5,000 samples, 128/400 features, three outputs, intercept and penalty 10. Two fresh-process ABBA blocks, seven timed fits after warmup, gave paired median ratios 1.154 [1.025–1.514] and 1.193 [1.128–1.389]. All coefficients, intercepts and complete diagnostic reports match. This measures the admitted primal path's duplicate-diagnostic removal; it does not measure a complete forecast or fallback QR/SVD speed. The probed AutoReadout code is byte-identical to the retained implementation. The public workflow matrix above uses Ridge.

    An exploratory 400-unit float64 classic CPU compile probe observed a 45.54 s first compiled request. Warm 257-step forecasts took 37.99 ms versus 44.79 ms eager; 1,025-step forecasts took 106.82 ms versus 157.40 ms. Both complete predictions matched exactly. The second horizon reused the same 64-step compiled chunk cache; it is not a second cold start. One cold process and these synthetic signals do not establish a general compiler policy or chaotic-forecast accuracy. CPU teacher-forced sequences remain eager.

    These two probes have narrower provenance than the archived workflow harness. The readout probe isolates unchanged readout dependencies. Compilation used the then-live candidate checkout before the slicing rewrites were restored, without an isolated overall source manifest. Its timings remain historical candidate observations and do not establish final adopted-runtime speed. Compilation remains opt-in. Readout records and compile records retain their raw samples, diagnostics, native settings and warnings.

    CPU recurrence investigation¶

    After merging PR #466 as 3b34005, we profiled the complete public fit and history-plus-forecast workflows before choosing the next optimization. These experiments use fresh synthetic development data and fixed saved weights; they are neither another accuracy search nor a new comparison with competitors.

    On this Apple M5, recurrence is the main cost. In a separate instrumented 1,000-unit, batch-one dense fit, recurrent multiplication accounts for 54.7% of Torch self CPU time and tanh for 20.1%. The successful Ridge solve costs about 26 ms, versus about 25 ms for a direct SciPy diagnostic without ResDAG's guards. Transactional model copying accounts for roughly 1–1.6 ms in cProfile. Removing numerical guards or failed-fit isolation would miss the main cost. Profiler times identify work; the latency measurements below come from uninstrumented public calls.

    Optional sparse CPU execution candidate¶

    A private prototype substitutes SciPy CSR multiplication for Torch CSR multiplication, leaving projection, activation, leak, scaling, training and forecast commands unchanged. Both processes use the same 1,000-unit matrix with 6,070 stored connections, float64, batch one, 10,001 observations, 500 washout/history steps and a 553-step forecast. The fixed readout is Ridge, not AutoReadout. Construction is outside the clock; fit includes preprocessing, the complete training prefix and transactional commit. Forecast includes history replay. Lazy SciPy operator construction and every Tensor/NumPy bridge are inside the measured calls.

    Dense batch candidate and rejected alternatives¶

    At batch four, replacing one matrix multiplication with four matrix-vector multiplications improves public fit by 1.775×/1.798× and forecast by 1.929×/1.956× in the two processes. However, the changed reduction order produces substantially different fitted coefficients and closed-loop predictions on this poorly conditioned synthetic fixture. This candidate is not adopted. Those differences do not score physical-system accuracy, but they preclude calling the change numerically identical.

    At batch one, matrix-vector multiplication and transposing the dense equation provide no measured primitive benefit. Reusing tanh output storage also gives no meaningful gain in the bounded allocation probe. Torch CSR is slower than dense in the initial 1,000-unit public profile; compressed storage alone is not a speed guarantee. Sequential profile rows are not a paired storage comparison.

    Download raw timings, hashes, source manifests and diagnostic scripts. The earlier cross-library CPU gap remains open until an adopted implementation is measured on the same comparison protocol. Extending CPU teacher-forced compilation is deferred: its startup and maintenance costs are not justified by established workflow gains. The next work prioritizes standard PyTorch fit/forecast performance and composition inside larger GPU models, preserving gradients and device placement. CPU measurements do not establish GPU throughput.

    Run the capability protocol yourself¶

    From a repository checkout, install the optional dependencies and run the single-revision command. Generating TSDynamics observations requires Python 3.12 or newer:

    python -m pip install -e ".[hpo,dynamics]"
python -m pip install -r benchmarks/requirements.txt
python benchmarks/tuned_accuracy.py --mode capability --after HEAD \
  --test-seeds 401 402 403 404 405 --n-trials 24 \
  --artifacts-dir /tmp/resdag-capability --output capability.json

    It archives the committed source, generates the observations, records their versions and hashes, and freezes all four winners before evaluation. Use fresh output paths. To reuse saved observations exactly, add --data-dir /path/to/saved-data; that directory contains data.json, lorenz.npy and rossler.npy. For a bounded plumbing check, use --quick --n-trials 1 and omit --test-seeds; quick mode uses the separate smoke seed 101.

    This command repeats the protocol. Reusing seeds 401–405 reproduces an existing bank; it does not create a fresh test. A new scientific experiment needs a previously unused bank chosen before tuning. The measurements above used an archived external wrapper and its frozen workers; this later supported command was not their original driver. Backend and dependency differences can change numerical results.

    Stored models and regression anchors¶

    Four trained 4.1.0 checkpoints were loaded in both the published implementation and the corrected runtime. All 12 history-conditioned forecasts and their fitted tensor fingerprints were byte-identical. This checks materialized model behavior; it does not imply that newly constructed models keep the old draws. Current-memory and RNG round trips are also covered by the artifact test suite.

    Two existing CI quality tests had implicitly identified their reservoir weights only by a seed. Their strict bounds failed after those seeds generated different weights. The tests now use explicit public initializer callbacks to reproduce their historical weights. All 18 reservoir tensors match the pinned old implementation byte for byte. Seeds, target data and accuracy limits are unchanged; the FORCE suite and parallel forecast floor pass. Fresh-default skill is measured separately above.

    Compact storage and paired CPU execution¶

    For a fixed 400-unit model, compressed-only storage reduced the sparse cycle's retained tensor storage from 1,321,042 to 37,842 bytes, and the sparse random example from 1,351,978 to 58,466 bytes. These counts deduplicate tensor storage; they are not peak process-memory measurements. Read memory and sparse models for temporary initialization, feature-history, solver and device boundaries.
